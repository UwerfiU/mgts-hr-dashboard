# Backend дашборда стажировок МГТС

В кейсе МГТС HR отслеживает шестимесячную программу стажировок. В кейсе 5 стажёров и 5 наставников, шесть ежемесячных циклов и две разные анкеты с числовыми оценками и комментариями. История поступит в двух Excel-файлах, новые ответы — из внешнего сервиса анкетирования. Точные поля, шкалы и идентификаторы станут известны на финале. Сейчас работаем на синтетическом наборе. Финал включает автоматический сбор, динамику, сравнение сопоставимых оценок и AI-анализ комментариев с обоснованием сигналов для HR.

Backend отвечает за интеграции, импорт, хранение, права на детализацию, расчёты и API. Frontend визуализирует готовые результаты и разрабатывается параллельно на том же контракте.

## Источники и поток данных

**Новые ответы:** две анкеты → внешний сервис → Backend по расписанию получает ответы → проверяет, нормализует и сохраняет → API отдаёт аналитику → дашборд HR.

**История:** два Excel-файла → Backend читает каждый файл по настройкам его формата → та же проверка, нормализация и запись → тот же API → тот же дашборд. Исторические файлы загружаются напрямую в Backend. Создавать из них ответы в Google Forms не требуется.

Для локальной демонстрации рекомендую **Google Forms API с периодическим чтением ответов**. Backend сам делает исходящие запросы, поэтому публичный адрес не нужен. Для объёма кейса можно перечитывать все страницы ответов обеих форм и обновлять записи по паре `formId + responseId`. Это упрощает повторную синхронизацию и обработку исправленных ответов. На старте нужно проверить доступ команды к обеим формам, права OAuth и работу API с ноутбука, на котором будет защита. [Получение ответов](https://developers.google.com/workspace/forms/api/reference/rest/v1/forms.responses/list), [структура ответа](https://developers.google.com/workspace/forms/api/reference/rest/v1/forms.responses).

| Вариант | Когда выбрать и что проверить |
|---|---|
| **Google Forms → Google Sheets → Sheets API** | Запасной вариант, если связанный лист проще настроить и читать. Проверить права на обе таблицы и устойчивый ключ записи. Если своего ID нет, номер строки сам по себе ненадёжен при сортировке или удалении. [Связать форму с таблицей](https://support.google.com/docs/answer/2917686), [чтение через Sheets API](https://developers.google.com/workspace/sheets/api/guides/values). |
| **Apps Script → Backend** | Устанавливаемый триггер отправки формы может запускать HTTP-запрос. Выбирать, если нужна отправка по событию и есть доступный для Google защищённый адрес. Триггер из облака не сможет вызвать `localhost` ноутбука. [Триггеры Apps Script](https://developers.google.com/apps-script/guides/triggers/installable), [HTTP-запросы из Apps Script](https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app). |
| **Уведомления Forms API** | Для MVP избыточны: уведомления приходят в Cloud Pub/Sub, а за самими ответами всё равно нужно обращаться к API. [Уведомления Google Forms](https://developers.google.com/workspace/forms/api/guides/push-notifications). |

Для Excel достаточно на старте распознавать повтор **того же файла**. Если придёт исправленная версия без стабильных ID строк, её стоит загружать как явную замену предыдущей партии. Одинаковый балл или текст у двух людей сам по себе не означает дубль. Склеивать Excel и ответы формы можно только по подтверждённому ключу; до этого источники разделяются, например по согласованным циклам.

## Общий контракт Frontend и Backend

**Внутренняя модель.** Цикл имеет номер `1–6`. У анкеты есть роль и версия, у вопроса — внутренний ключ, тип и, для оценки, шкала. Отправка хранит источник, ключ записи в источнике, цикл и роль; связь с тем, **о ком** дан ответ, опциональна. В частности, анкета наставника попадёт в карточку стажёра только при наличии надёжного способа определить, к кому она относится. Backend настраивает преобразование «Excel-столбец или ID вопроса формы → внутренний вопрос», а отдельно — «внутренние вопросы → показатель и допустимое сравнение». Frontend этих преобразований не знает.

**Три маршрута для первого этапа:**

| Маршрут | Вход и результат |
|---|---|
| `GET /api/v1/meta` | Циклы, каталог показателей с названиями и шкалами по ролям, разрешённые псевдонимы, доступные категории, признаки доступности детализации и AI, режим данных и статус синхронизации. |
| `GET /api/v1/metrics` | Параметры: `fromMonth`, `toMonth`, `metricId`, опционально `internId`, `mentorId`. Возвращает охват по ролям для выбранного среза, точки динамики и распределение выбранного показателя, а также расхождения, если они рассчитаны. |
| `GET /api/v1/feedback` | Тот же срез по месяцам и разрешённым идентификаторам, плюс опционально `role` и `categoryId`. Возвращает разрешённые к показу комментарии или сообщение о недоступности. На финале сюда можно добавить статус анализа, сводки и сигналы по тому же срезу. |

Импорт и синхронизация запускаются на стороне Backend. Для MVP не требуется делать административные экран и API для загрузки файлов или создания анкет.

**Пример формы ответа `/metrics`** для одного месяца на моках. Это пример контракта, а не структура будущего Excel.

```json
{
  "dataMode": "demo",
  "metricId": "demo_metric",
  "coverage": {
    "intern": { "submitted": 5, "expected": 5 },
    "mentor": { "submitted": 4, "expected": 5 }
  },
  "series": [
    { "role": "intern", "points": [{ "month": 1, "value": 3.8, "n": 5 }] },
    { "role": "mentor", "points": [{ "month": 1, "value": 3.25, "n": 4 }] }
  ],
  "distribution": [
    { "role": "mentor", "buckets": [{ "score": 3, "count": 3 }, { "score": 4, "count": 1 }] }
  ],
  "comparison": {
    "status": "available",
    "direction": "intern_minus_mentor",
    "points": [{ "month": 1, "value": 0.5, "nPairs": 4 }]
  }
}
```

- **Графики.** Backend возвращает упорядоченные точки по циклам и число валидных наблюдений `n`; Frontend рисует график. Пропущенная точка содержит `value: null`, а не `0`. При неизвестном плане ответов `expected: null`, и карточка не показывает процент. Запрещённую детализацию API обозначает отдельно от пустого результата.
- **Сравнение.** На моках можно взять среднюю разницу внутри сопоставленных пар «стажёр × цикл». Например, `0.5` выше рассчитано только на четырёх парах; вычитание средних по всем ответам дало бы другую величину. Это тест правила отображения, а не утверждённая формула. На финале сравнивать можно только вопросы об одном аспекте с согласованной шкалой. Если связи между людьми нет, парные расхождения недоступны. Сводное сравнение групп возможно отдельно, если вопросы и выборки позволяют его обосновать.
- **Идентификаторы.** `internId` и `mentorId` — непрозрачные стабильные коды. Фильтр по наставнику на обзоре выбирает связанные пары «стажёр × цикл», если такая связь подтверждена; роль автора комментария задаётся отдельно. Если данных для связи нет или её использование запрещено, Backend не отдаёт персональные фильтры и отклоняет соответствующие запросы. При полной анонимности восстановить индивидуальную историю нельзя. Для неё нужны согласованные псевдонимы, повторяемые из месяца в месяц. С пятью участниками одного псевдонима недостаточно для защиты: подробный комментарий или слишком узкий срез может раскрыть автора. Разрешение на показ числовой истории и отдельных текстов следует проверять отдельно.
- **Mock / реальный API.** Один клиент и две реализации: локальные фикстуры и HTTP. Переключатель задаётся конфигурацией запуска. Фикстуры повторяют контракт и поддерживают те же фильтры и состояния. При ошибке Backend интерфейс показывает ошибку; переход на синтетические данные возможен только явным переключением режима.

## Стек

- Python, FastAPI и Pydantic для одного локального HTTP-сервиса с OpenAPI. [Документация FastAPI](https://fastapi.tiangolo.com/features/).
- SQLite для локального хранения и `openpyxl` для чтения `.xlsx`.
- Python-модуль расчётов внутри Backend. На финале в том же сервисе добавляется модуль анализа комментариев. Модель выбирается после знакомства с текстами и условиями обработки.

## Порядок работы

1. Согласовать три маршрута, внутренние сущности, коды недоступности и фикстуры. На тестовом аккаунте проверить доступ к двум формам по API.
2. Поднять БД, нормализацию и API на синтетическом наборе. Сверить результаты фильтров с ожидаемыми значениями из фикстур.
3. Проверить импорт на двух тестовых Excel, включая валидацию строк и повтор загрузки. Подключить одну схему автоматической синхронизации обеих тестовых форм.
4. Перед показом ввести новый ответ, дождаться записи, увидеть изменение API и дашборда, повторить синхронизацию и проверить отсутствие дублей. Вариант запуска на сохранённом наборе должен работать без интернета.
5. На финале настроить фактические поля и циклы, проверить пересечение источников и допустимость сравнения. Привязки, пороги и решение о показе текстов согласовать после изучения данных. Затем включить AI и проверить основания выдаваемых сводок и сигналов.

## Готовность прототипа

- [ ] Три маршрута возвращают ожидаемые данные на общем наборе. Без разрешённой связи индивидуальный срез недоступен на уровне API.
- [ ] Импорт двух тестовых Excel даёт отчёт. Повтор того же файла не удваивает данные.
- [ ] Ответ из внешней формы появляется в локальном API автоматически в пределах настроенного интервала.
- [ ] Ошибка внешней синхронизации не стирает историю. Известно время последнего успешного получения ответов.
- [ ] Участник команды запускает сервис по инструкции с синтетической БД. Секреты и реальные данные хранятся вне репозитория.
