# Общий план реализации бэкенда (MGTS HR Dashboard)

Нормативный документ по контракту с фронтом и критериям готовности — **BACKEND.md**.
Этот план: финальная архитектура, целевая структура репозитория, список работ для
субагентов (с зависимостями и критериями) и судьба уже написанного скелета.

## 1. Финальная архитектура (слитая версия)

```
 ИСТОЧНИКИ                      НОРМАЛИЗАЦИЯ                  ХРАНИЛИЩЕ              АНАЛИТИКА → API
 ┌─────────────────────┐      ┌──────────────────┐      ┌──────────────────┐   ┌────────────────────────┐
 │ Excel × 2 (история) │──CLI─▶│                │      │  SQLite          │   │                       │
 │                     │ dry-  │  Source Adapters │─────▶│  нормализованная │──▶│  Analytics-модуль:    │
 └─────────────────────┐ run,  │  (xlsx / forms)  │      │  модель данных   │   │  coverage, series,    │
                       │ отчёт │  + Validation     │      │  + provenance    │   │  distribution,        │
 ┌─────────────────────┴───────│  (цикл, шкалы,    │      └──────────────────┘   │  comparison (пары)    │
 │ Google Forms × 2 (новое)    │   пустые ≠ 0)     │                            │                        │
 │   poller: старт + интервал, │                    │      ┌──────────────────┐   │  Сигналы (этап 2):   │
 │   upsert по formId+respId   └────────────────────│─────▶│  Каталог: анкеты, │──▶│  правила + причины  │
 └─────────────────────────────                     │      │  вопросы→метрики, │   │  AI-модуль (этап 2):│
                                                    │      │  пары сравнения   │   │  темы/сводки/риск   │
                                                    │      └──────────────────┘   └─────────┬────────────┘
                                                    │                                       ▼
                                                    │                        GET /api/v1/meta|metrics|feedback
                                                    │                                       ▼
                                                    │                              Frontend (фикстуры или HTTP)
```

Ключевые принципы (из BACKEND.md, принимаем все):
- **Один канонический тип записи** из двух разных источников; маппинг «столбец Excel / ID вопроса формы → внутренний вопрос» живёт в конфиге бэкенда, фронт его не знает.
- **Идемпотентность**: повтор того же файла/ответа не дублирует данные (уникальность по `source + source_key`); исправленная версия Excel — явная замена партии.
- **Права на детализацию**: персональные срезы (`internId`, `mentorId`) доступны только при подтверждённой связи и разрешении; «запрещено» API отличает от «пусто». Числовая история и тексты разрешаются отдельно.
- **Mock/реальный режим**: у фронта один клиент, две реализации (фикстуры / HTTP), переключатель в конфиге запуска; фикстуры повторяют контракт, включая фильтры и состояния недоступности.
- **Сбой внешней синхронизации не стирает историю**; в `/meta` видно время последней успешной синхронизации и ошибку.

От моего скелета сохраняем (это ускорит этап 2):
- абстракция LLM-клиента (OpenAI-совместимый эндпоинт) + лексиконный fallback — «ошибка модели не блокирует числовую аналитику»;
- детерминированные правила сигналов с человекочитаемыми причинами (основа B8);
- подход к тестам: TestClient + изолированная БД через env.

## 2. Целевая структура репозитория

```
mgts-hr-dashboard/

├── PLAN.md                     # этот документ
├── README.md                   # quickstart (WP6)
└── backend/
    ├── requirements.txt        # + openpyxl, apscheduler (или простой цикл)
    ├── .env.example            # ключи Google OAuth, режимы — только примеры
    ├── config/                 # ← НОВОЕ: всё настраиваемое, без кода
    │   ├── catalog.yaml        # анкеты (роль, версия), вопросы (ключ, тип, шкала), метрики, пары сравнения
    │   ├── sources_excel.yaml  # файл → роль, лист, маппинг столбцов→вопросы, правило цикла, ключ записи
    │   ├── sources_forms.yaml  # formId ×2, интервал синхронизации, маппинг ID вопросов→внутренние
    │   └── permissions.yaml    # dataMode, разрешены ли персональные срезы/тексты, минимальный объём для вывода
    ├── app/
    │   ├── main.py             # FastAPI, lifespan: init_db + старт poller'а
    │   ├── config.py           # pydantic-settings (env MGTS_*), пути, режимы
    │   ├── db/                 # engine/session; модели (см. §3)
    │   ├── catalog/            # загрузка config/catalog.yaml в БД, API каталога для аналитики
    │   ├── sources/
    │   │   ├── base.py         # SourceAdapter: read() → RawRecord(source, source_key, payload)
    │   │   ├── excel_importer/ # CLI: dry-run, отчёт (принято/пропущено/ошибки), идемпотентность, замена партии
    │   │   └── forms_poller/   # Google Forms API (list responses, страницы), upsert; sync_state (last_ok, error)
    │   ├── normalization/      # маппинг по конфигам, валидация (цикл 1–6, шкалы, пустые≠0), provenance
    │   ├── analytics/          # coverage, series(n), distribution, comparison; сигналы (этап 2)
    │   ├── ai/                 # llm_client + анализ комментариев (этап 2); результат хранится отдельно
    │   └── api/v1/             # meta.py, metrics.py, feedback.py (+ codes.py: коды недоступности)
    ├── fixtures/               # JSON-фикстуры контракта для фронта (все фильтры и состояния)
    ├── data/                   # xlsx-датасеты, mgts.db (БД в .gitignore)
    └── tests/                  # по WP: нормализация, импорт, poller (mock), API на фикстурах
```

## 3. Модель данных (нормализованная, из BACKEND.md B1)

| Сущность | Поля (ключевые) | Комментарий |
|---|---|---|
| `Questionnaire` | role (intern/mentor), version | версия анкеты |
| `Question` | questionnaire_id, key, label, type (score/text), scale_min, scale_max | добавление/переименование — через конфиг, не через миграции |
| `Metric` | id, role, question_keys[] | каталог показателей; вопрос→метрика в конфиге |
| `ComparisonPair` | metric_a, metric_b (или вопросы), direction, rule | только явно настроенные пары |
| `Intern` / `Mentor` | opaque_id (стабильный код), alias (псевдоним), real_name (вне репо) | связь «о ком» у отправки — опциональна |
| `Submission` | source (excel/form), source_key (file+row_hash / formId+responseId), cycle 1–6, role, about_intern_id?, submitted_at, file_batch_id? | уникальный ключ идемпотентности: `(source, source_key)` |
| `Answer` | submission_id, question_key, score (nullable), text (nullable) | пропуск оценки = NULL, не 0 |
| `SyncState` | connector, last_success_at, last_error, cursor/page info | для `/meta` и диагностики |

Связь «наставник → о каком стажёре» хранится только при надёжном определении
(подтверждённый ключ/псевдоним); иначе отправка учитывается в агрегатах, но не
попадает в карточку стажёра.

## 4. API (контракт BACKEND.md, без изменений)

- `GET /api/v1/meta` — циклы, каталог метрик по ролям с названиями и шкалами, разрешённые псевдонимы/категории, флаги доступности детализации и AI, dataMode, статус синхронизации.
- `GET /api/v1/metrics?fromMonth&toMonth&metricId[&internId|mentorId]` — coverage по ролям (submitted/expected, expected=null при неизвестном плане), series с `n`, distribution, comparison (только для настроенных пар; `value: null` вместо 0).
- `GET /api/v1/feedback?fromMonth&toMonth[&role|categoryId|internId]` — разрешённые комментарии или **код недоступности** (отдельно от пустого среза). Этап 2: сюда добавляются статус AI, сводки и сигналы по тому же срезу.

Плюс служебные (не часть контракта фронта): `GET /health`; импорт — только CLI;
синхронизация форм — автоматически (старт + интервал), вручную — рестарт/перезапуск poller'а.

## 5. Работы для субагентов

Каждый WP = отдельная задача с чёткой границей файлов и критерием готовности
(колонка «Критерий» из BACKEND.md). Порядок запуска:

```
WP0 → WP1 → WP2 → ┬→ WP3 (Excel)  ─┐
                  ├→ WP4 (Forms)   ─┼→ WP6 (запуск/доки)
                  └→ WP5 (API+фикстуры, параллельно с 3–4 на фикстурах)
Этап 2 (когда придут материалы): WP7 → WP8 ∥ WP9
```

| WP | Задача | Файлы/модули | Зависимости | Критерий готовности (кратко) |
|---|---|---|---|---|
| **WP0** | Чистка скелета под целевую структуру: requirements (+openpyxl), config/, удаление webhook/CSV-кода, каркас каталога конфигов, seed синтетики | backend/* (каркас) | — | Репозиторий соответствует §2; `pytest` зелёный на заглушках; инструкция запуска работает |
| **WP1** | B1: модель данных + каталог (анкеты/вопросы/метрики/пары), загрузка конфигов в БД | app/db/models.py, app/catalog/, config/*.yaml | WP0 | Вопрос добавляется/переименовывается через конфиг без изменения таблиц и схемы API; ответ «без связи» хранится |
| **WP2** | B2: нормализация — адаптеры источников → каноническая запись, валидация цикла/шкал/пустых, provenance, отчёт об отклонениях | app/sources/base.py, app/normalization/, config/sources_*.yaml | WP1 | Два формата дают один тип записи; отклонённые строки видны с причиной; пропуск ≠ 0 |
| **WP3** | B3: CLI импорта двух Excel — dry-run без записи, отчёт принятых/пропущенных/ошибочных, идемпотентность файла, явная замена партии | app/sources/excel_importer/, tests | WP1–2 | Повторный импорт того же файла не увеличивает число ответов; отчёт полный |
| **WP4** | B4: коннектор Google Forms — OAuth-чеклист, poller (старт+интервал), upsert по formId+responseId, sync_state; **mock-коннектор синтетических ответов для офлайн-демо**; проверка доступа к формам с ноутбука защиты | app/sources/forms_poller/, config/sources_forms.yaml | WP1–2 | Новый ответ появляется в API в пределах интервала; повторное чтение без дублей; при сбое видны ошибка и время последнего успеха |
| **WP5** | B5: `/api/v1/{meta,metrics,feedback}` + analytics-модуль (coverage/series/distribution/comparison) + **фикстуры для фронта** (все фильтры, состояния «пусто» vs «запрещено») | app/api/v1/, app/analytics/, fixtures/ | WP1–2; согласованный контракт | Фильтры дают ожидаемый результат на синтетике; пустой срез ≠ запрещённая детализация; ограничения действуют на сервере |
| **WP6** | B6: README quickstart, запуск с заполненной синтетической БД без внешних ключей и офлайн, пример конфигов, секреты вне репо | README.md, config/, scripts seed | WP3–5 | Другой участник поднимает проект по инструкции; в репо нет ключей и реальных данных |
| **WP7** (этап 2) | B7: сопоставление фактических полей Excel/форм, циклы, сравнимость вопросов, правила связывания, пересечение истории и новых ответов | config/* (перенастройка), normalization | материалы организаторов | Контрольные строки из обоих Excel сверены с БД; известно, что можно объединять |
| **WP8** (этап 2) | B8: методика сравнения и сигналы — пороги, минимальный объём, для каждого сигнала «польза + следующее действие HR»; объяснение «почему сигнал / почему данных мало». Основа — правила из скелета (`services/signals.py`) | app/analytics/signals.py | WP7 | На контрольных примерах команда вручную воспроизводит расчёт |
| **WP9** (этап 2) | B9: AI-модуль — тематизация и сводки по разрешённым текстам, хранение результата отдельно (период, охват, ссылки на основания), выбор модели после знакомства с текстами. Основа — `ai/llm_client.py` + fallback из скелета | app/ai/, расширение /feedback | WP7; доступный запуск модели | Сводка подтверждается текстом, не раскрывает личность, нет выводов при недостатке данных; ошибка модели не блокирует числовую аналитику |

## 7. Открытые решения (закрыть до старта соответствующих WP)

1. **Доступ к Google** (до WP4): кто создаёт две тестовые формы и даёт доступ сервисному аккаунту; проверить OAuth и API именно с ноутбука защиты (BACKEND.md, шаг 1).

4. **AI-модель для финала** (до WP9): что доступно — внешний OpenAI-совместимый API или локальная модель (на машине есть LM Studio).
5. **Пороги сигналов и минимальный объём данных** (WP8): после изучения реальных текстов и оценок.

## 8. Критерий готовности прототипа (из BACKEND.md, повторяем для контроля)

- [ ] Три маршрута возвращают ожидаемые данные на общем наборе; без разрешённой связи индивидуальный срез недоступен на уровне API
- [ ] Импорт двух тестовых Excel даёт отчёт; повтор того же файла не удваивает данные
- [ ] Ответ из внешней формы появляется в локальном API автоматически в пределах интервала
- [ ] Ошибка синхронизации не стирает историю; известно время последней успешной синхронизации
- [ ] Участник команды запускает сервис по инструкции с синтетической БД; секреты и реальные данные вне репозитория

**Демо на защите** (флоу из задания): новый ответ в форме → poller подхватывает в пределах интервала → видно изменение `/metrics` и дашборда → повторная синхронизация без дублей. Офлайн-вариант — mock-коннектор с синтетическим ответом.
